## 1. Goals

- Four asymmetric classes with conflicting interests and temporary alliances.
- Playable in short matches; difficulty modes scale depth and length.
- 1 to N players per class (teams), with bots filling empty seats.
- Looks and feels real-time while resolving in simultaneous rounds.
- Mostly UI; a small reactive 3D city in the center of the screen.

## 3.1 Code model: hybrid (D-029)

Four kinds of code, each with a clear rule. When adding something new, decide
which kind it is first.

| Kind | Use for | Form | Examples |
|---|---|---|---|
| **State** | Anything saved, sent, hashed, replayed, or simulated | Plain typed tables. No metatables, functions, Instances, or cycles; string-keyed | `MatchState`, `ClassState`, `LineState`, `Bill`, `TradeOffer`, `Promise`, `Alliance`, `LogEntry` |
| **Behavior** | Logic that differs by kind | Stateless strategy classes, one abstract base per family, inheritance depth max 1 | `Step`, `Policy`, `PromiseRules`, `Objective`, `GameEvent`, `InfoMode`, `ClassRules`, `LineRules`, `BotStrategy` |
| **Operations** | Logic that doesn't vary | Function modules over state | `Bills`, `Trade`, `Alliances`, `Reputation`, `StateOps` |
| **Objects** | Things with identity, lifecycle, or dependencies | Classes | `Match`, `RuleSet`, `Rng`, services, `PhaseScheduler`, `Seat`, `RemoteHandler`, `RateLimiter`, `Replicator`, `Signal`, `NetClient`, `Store`, city view classes |

### State rules

- All state types live in `shared/Game/Types.luau`.
- State must pass `assertSerializable` (a test helper): only numbers, strings,
  booleans, and tables with string or integer keys.
- Entities are referenced by **string id**, never by object reference.
- Snapshot = `StateOps.deepCopy(state)`; hash = `StateHash.compute(state)`
  (deterministic: sorted keys). No per-class serialize/deserialize code.

### Behavior rules

- A behavior class is **stateless** (it may hold config passed to its
  constructor). Everything it needs arrives as arguments:
  `run(state, ctx)`, `audit(state, promise)`, `apply(state, ...)`.
- Behaviors are looked up from **registries** keyed by id or kind
  (`PolicyRegistry`, `LineRules` by line type, `ClassRules` by class id), so
  adding a new policy or line type means adding one file and one registry
  entry.
- Abstract methods raise `error("not implemented: Class:method")`.

```lua
--!strict
-- Behavior example: stateless, operates on plain state.
local Types = require("../Types")
local LineRules = require("./LineRules")

local FactoryRules = setmetatable({}, { __index = LineRules })
FactoryRules.__index = FactoryRules

function FactoryRules.new(config: Types.LineConfig)
	return setmetatable({ _config = config }, FactoryRules)
end

-- Output depends on the owner's Education stock (see GAME_DESIGN 6.1).
function FactoryRules:output(line: Types.LineState, owner: Types.ClassState, staffed: number): number
	local base = staffed * self._config.outputPerSlot
	if owner.stock.education < 1 then
		return base // 2
	end
	return base
end

return FactoryRules
```

(The `require` form depends on the test-strategy decision D-014; follow
whatever convention M0-T4 records.)

### Mutation and atomicity

- `Match:resolveDay(rng)` deep-copies the state into a **working copy**, runs
  the `ResolutionPipeline` on it, and commits it only if every step succeeds.
  A thrown error leaves the real state untouched and is logged.
- Steps mutate the working copy **only through `StateOps` helpers** (safe
  resource add/subtract with non-negative checks), never by ad-hoc field
  writes scattered around.
- Live actions (`Match:applyTrade`, `proposeBill`, ...) validate first, then
  mutate through the same helpers.
- For tests and debugging, `ctx.trace` can record a snapshot after each step.

### Determinism

No Roblox services or Instances in `shared/Game`; randomness only via the
injected `Rng`; ordered iteration (`CLASS_ORDER`, sorted ids), never
order-dependent `pairs`.

### Conventions for classes

- One class per file; file name = class name; `ClassName.new(...)`; `:` for
  methods, `.` for statics; fields prefixed `_` are private; exported instance
  type; `--!strict`.
- Inject dependencies (Rng, RuleSet, config); no globals, no `_G`, no hidden
  singletons. Services receive their dependencies in `new`.
- Never reach into another object's `_field`.

### Key pieces

| Piece | Responsibility |
|---|---|
| `Match` (class, facade) | Holds `MatchState`, `RuleSet`, `Rng`; `resolveDay`, live actions, `snapshot`, `hash`, `viewFor(class)` |
| `RuleSet` (class) | Wraps difficulty flags and config; answers "is policy X enabled", "market cap", "needs multiplier" |
| `StateFactory` | Builds the initial `MatchState` from config, seats, seed |
| `Step` + 13 subclasses, `ResolutionPipeline` | One resolution step each, `run(state, ctx)`; the pipeline runs R1..R14 in order |
| `ClassRules`, `LineRules`, `Policy`, `PromiseRules`, `Objective`, `GameEvent` | Polymorphic behavior on plain state |
| `InfoMode` strategies + `PlayerViewBuilder` | Per-player views for each info mode |
| `Bills`, `Trade`, `Alliances`, `Reputation` (modules) | Validation and effects of politics and diplomacy |
| `Service` (abstract) + services; `PhaseScheduler`; `Seat`, `SeatRegistry`; `RemoteHandler` + handlers; `RateLimiter`; `Replicator` | Server runtime |
| `BotStrategy` + 4 subclasses | Heuristic play per class (server) |
| `Signal` | Minimal event class (no Instances) |
| `NetClient`, `Store` | Client networking and observable state |
| `CityView`, `LineVisual`, `CityAnimator` | 3D city view classes |

The **UI tree is not class-based**: React function components with hooks
(composition, D-028). It reaches game data only through `Store`.

## 5. Core model

### 5.1 Entities

- **Match**: id, difficulty, round number, phase, class states, policy state,
  event log.
- **Class** (`Working | Middle | Capitalist | State`): resources, goals,
  assigned seat(s), win progress.
- **Seat**: a human player, a bot, or a team of humans controlling one class.
- **Team roles** (2+ players on one class): split responsibilities (Economy,
  Politics, Diplomacy) per D-007; details in `docs/GAME_DESIGN.md` section 14.
- **Promise**: a recorded agreement between classes (not enforced). Used by
  `Reputation`.

### 5.2 Resources

Defined in `docs/GAME_DESIGN.md` sections 4 to 6 (six resources, four line
types). Code reads them from `Config/*`.

## 6. Round engine (the "hidden turns" design)

The match advances in **rounds**. Each round has soft phases that the UI
dresses up as in-world time (market hours, council session) rather than
"Turn 3".

```
ActionWindow (60-90s, simultaneous)
  - players plan, chat, make and accept trade offers, set policy stances
  - every player submits an ActionSet; can edit until the timer ends
        |
Resolve (server, instant)
  - Match:resolveDay(rng) -> events (runs the ResolutionPipeline of Step objects)
  - production, trade settlement, policy effects, upkeep
        |
Reveal (5-10s)
  - city animates results; events shown; hidden info updated per class
        |
Victory check -> next round or end match
```

Rules:

- **Simultaneous submission.** Nobody waits on another player's turn.
- **Timer ends the window.** Missing submissions default to "no action" (or a
  bot suggestion on easy modes).
- **Always something to do** during the window: trade, chat, plan, read.
- **Resolve is deterministic.** Same starting snapshot + same actions + same
  RNG seed = same result. This enables tests, replays, and debugging.

## 7. Policy and trade

- **Policies** are data in `Config/Policies.luau`: each has per-class effects
  and a vote rule. Votes are resolved during `Resolve`.
- **Trade offers** are messages between classes during the window. Accepted
  trades are *settled by the engine only for the part that is immediate*
  (e.g. a swap executed now). Future promises are recorded, not enforced.
- **Reputation** records kept/broken promises per class (and optionally per
  player) and is visible to others. It can carry across matches via
  persistence (V2, D-015 deferred).

## 8. Victory

`Victory.check(state)` returns one of:

- `{ kind = "none" }`
- `{ kind = "solo", class = ... }`
- `{ kind = "shared", classes = { ..., ... } }`

Shared wins require both classes' conditions to be satisfied and an active
agreement between them. Thresholds come from `Config/Difficulty.luau`.

## 9. Difficulty modes

Defined as config, not code branches:

| Mode | Idea |
|---|---|
| Easy | Reduced mechanics, short rounds, hints on, no hidden info. Doubles as tutorial. |
| Normal | All four classes, core systems, ~30 min. |
| Hard | Full policy system, events, hidden information. |
| Extreme | Everything, long match, harsh economy, minimal hints. |

Each mode toggles features and tunes numbers via `Difficulty.luau`.
`Match.create(config)` reads these; game logic never checks mode names.

## 10. Networking

- Typed remotes defined once in `shared/Net/Remotes.luau`.
- **Client to server: intents only.** Examples: `SubmitActions`,
  `ProposeTrade`, `RespondToTrade`, `CastPolicyVote`, `SendChat`.
- **Server to client: filtered views.** `Replication` builds a per-player view
  of the match (own class fully, others partially, per difficulty rules) and
  sends diffs or snapshots.
- Every server handler: authenticate seat, validate payload shape, validate
  against current phase and state, then apply.
- Rate-limit chatty remotes (chat, trade proposals).

## 11. Client architecture

- `Store` holds the latest replicated view plus local UI state.
- React-Lua components subscribe to the store and render panels.
- Layout: central city viewport; each player's panel docked to a corner;
  shared elements (timer, event ticker, policy board) in consistent places.
- UI library: React-Lua (D-002). Fusion is the documented fallback.
- The city renderer reads the same view and animates from events; it holds no
  game truth.

## 12. Bots

`BotService` fills empty seats by producing an `ActionSet` through the same
pipeline as humans. Start with simple heuristic bots (goal-driven, mild
randomness). Bots must not get information a human in that seat wouldn't.

## 13. Persistence and meta (later)

- Ranks, leaderboard, cosmetics, reputation history.
- Profile library chosen in M14 (D-015).
- Keep strictly separate from match logic; matches should run without it.

## 14. Testing and verification strategy

- **Local (L1):** `scripts/check` = stylua, selene, strict type check, build, and
  Lune tests. Details and rules: `docs/VERIFICATION.md`.
- **Headless tests run the real code.** `tests/loader.luau` mounts `src/` as a
  virtual instance tree so Roblox-style requires (`script.Parent.X`) work under
  Lune; tests never contain copies of game code. Everything in
  `shared/Game` and `Config` must be testable this way (hence no Roblox services
  there). Test files are registered in `tests/run.luau`.
- **Unit tests** for everything in `shared/Game` and `Config` validation.
- **Scenario tests**: scripted multi-day matches with fixed RNG seeds that assert
  end states (including betrayal and shared victory).
- **UI rules lint** (`tests/ui_rules.luau`) and the dev-time `ChildrenGuard`.
- **Studio checks (L2)** by the agent through the MCP for anything that runs in
  Roblox (server, client, UI, networking); **owner checks (L3)** only for
  appearance and feel.

## 15. Build order (summary; authoritative version is `docs/ROADMAP.md`)

1. **Scaffold**: toolchain, Rojo project, Wally, lint/format, empty services.
2. **Domain core**: code-model foundation, `Match` facade, `ResolutionPipeline` with 1 resource per
   class, and tests.
3. **Server loop**: `MatchService` runs phases on a timer using the core.
4. **Net + Replication**: typed remotes, per-player views.
5. **Minimal UI**: one panel per class showing resources, a timer, and a
   submit button. No city yet.
6. **Trade**, then **policy votes**, then **victory**.
7. **Bots** so a solo player can test a full match.
8. **City visuals** and polish.
9. **Difficulty modes**, tutorial (Easy = guided match), then meta systems.
